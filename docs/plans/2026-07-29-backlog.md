## 1-7. Defects

### 1. Join shows your last-played save, and the "aboard" toast is premature

CONFIRMED, root cause found (verified).

**The toast is not an ordering bug, it is the wrong signal entirely.** `Plugin.cs:892` emits
"Aboard the host's ship!" from inside the `OnLobbyJoined` handler, gated only on
`joinedExistingPlayer` (`Plugin.cs:853-863`) which means nothing more than "this Steam lobby has at
least one other member". Its own comment shows the gate was only ever designed to stop a SOLO HOST
seeing the message; it was never a proxy for being aboard. The real aboard milestone is
`ForceEmbarkLocalPlayer` (`BoatStateApplicator.cs:1519-1525`) and it emits no toast at all, only a
log line at `:471`.

Consequences beyond the reported one: the same toast fires when the host is **on land** (nobody is
aboard any ship), and when the host **refuses admission** (the guest is quit 45s later by the
watchdog).

Toast-to-embark gap is variable, roughly 3s best case to 65s+ worst (30s host-defer cap if the host
is asleep, plus a 30s scene-load timeout). An earlier "15-20s" estimate was wrong.

**The world on screen is by design.** Title-screen path byte-copies the guest's most-recently-modified
solo slot to phantom slot 99 (`CoopSave.PickSoloSlot` -> `File.Copy`) **on a first join only**;
subsequent joins reuse the existing `coop_session_<hostId>.save`. Mid-game path is already sitting in
the real solo slot. The mod loads a guest world first deliberately, so the in-game join path runs
against a fully-loaded client (`TitleJoinManager.cs:9-16`).

- **Fix (small, recommended):** retitle `Plugin.cs:892` to a progress message ("Connected to {host},
  loading their world..."), and emit the real toast after the embark succeeds at
  `BoatStateApplicator.cs:420-428`, gated on `!packet.IsRecovery` and the `ForceEmbarkLocalPlayer`
  return, with wording branched on `packet.IsHostOnBoat`. `TeleportPlayer` has exactly one caller, so
  no other path is affected.
- **Bonus, orthogonal:** the host's remote avatar currently appears standing in the guest's own world
  during the pre-snapshot window. Gate the `PlayerPosition` apply on `HasReceivedWorldState`.
- **Note:** the black screen is still optional polish, but the toast fix is the actual bug and should
  land first.

### 2. Players fall from the sky on join

CONFIRMED, root cause found. (The verifier rejected the finding's git archaeology but not its
mechanism; the mechanism below is the corrected version.)

The join teleports the guest to **host boat position + 50m up** as a terrain-load perch
(`BoatStateApplicator.cs:123`, applied `:147-167`), then leaves them there through a 2s wait plus a
scene-load wait (up to 30s) before the real placement teleport at `:420`.

**There is no `Refs.SetPlayerControl(false)` anywhere in the join path.** A grep of
`BoatStateApplicator.cs` returns only lines 426 and 495, both `true` - the join re-enables a control
it never disabled. So the CharacterController stays live for the whole perch window: gravity and WASD
act, and the guest free-falls 50m in full view.

Second half of the defect: `PlayerSyncManager.Update` has no join gate, so the falling position is
streamed at 20Hz and **the rest of the crew watches the joiner drop out of the sky** too.

- **Fix (small, recommended):** add `Refs.SetPlayerControl(false)` immediately before the perch
  teleport at `:147`. Lines 426 and 495 already re-enable on both normal and throwing exits, so most
  of the plumbing exists. Companion: gate the sender in `PlayerSyncManager.Update` on
  `IsJoinInProgress`.
- **Do NOT** simply shrink the 50m lift. The perch exists to avoid materialising inside not-yet-loaded
  terrain, and `:1448-1456` was written to fix the historical guest-spawns-under-pier failures.
- Blackout as a cover has a real hazard: `Blackout.FadeTo` lerps on SCALED `Time.deltaTime`, so at
  `timeScale 0` the fade never completes and you get a permanent black screen instead of a fall.

### 3. Remote avatars float 2-3 inches above the deck, but stand flush on crates

**MY EARLIER SUSPICION (hardcoded eye-height constant) IS REFUTED.** The 1.7 eye height never runs on
the deck path, and the 0.9 capsule constant cancels exactly. A hardcoded-constant bug cannot produce a
deck/crate contrast, because a crate would show it too.

**The mod's arithmetic is exact and self-cancelling.** The sender transmits the CharacterController's
capsule bottom in boat-local coords (`PlayerSyncManager.cs:359/367`, gap read from live geometry); the
receiver adds 0.9 and the body fit subtracts 0.9, which cancel. What the soles are planted on is the
**walk collider's** deck surface re-expressed in the **visual** frame. The rendered deck planks are a
different mesh, and the simplified walk surface is authored above them. The float is that clearance.

Crates are flush because vanilla's `ItemRigidbody.MoveItemToWalkColRigidbody` maps them physics ->
visual by the SAME rule, so a crate's rendered top already carries the identical offset.

**CHEAP TEST BEFORE WRITING ANY CODE:** under this root cause, a crate resting on a deck must hover by
the same 2-3 inches **in vanilla singleplayer too**, and the amount should differ between boat models.
If that is true this is vanilla geometry, not a mod defect, and the only sane fix is cosmetic
compensation. Confidence is medium and the verifier did not fully endorse it; the numeric clearance is
prefab geometry, not code, so it cannot be settled by reading source.

- **Do NOT** ship a blanket config offset first: because crates carry the same offset, subtracting a
  delta would make avatars standing on crates SINK by that amount. The crate case is currently correct.
- **ADJACENT REAL DEFECT found in passing, worth fixing regardless:** `RemotePlayerManager.cs:714` adds
  +0.9 along the BOAT's up, while the body's -0.9 at `:780` is along WORLD up (the root is forced
  yaw-only at `:744`). On a heeled boat these stop cancelling: **at 10 degrees of heel the avatar sinks
  1.4cm and slides 15.6cm sideways.** Fix by placing the root at the feet.

### 4. Crouch feet are vertical (tippy-toes) instead of flat

CONFIRMED, root cause found (verified). My suspicion was right.

`SolveLegIk` is a 2-bone solver (hip + knee only). The foot transform is discovered and used ONLY as a
position sample at bind time; **its rotation is never written anywhere in the mod** (grep for
`.rotation =`, `localRotation =` and `.Rotate(` across src returns zero foot writes). The Synty chain
is UpperLeg -> LowerLeg -> Foot, so the foot rigidly inherits the shin's world rotation.

The squat drops the hip `CrouchDropMeters` (0.6m) while the ankle stays planted, and the IK pole pushes
the knee FORWARD, so the shin runs from a forward-high knee to a rearward-low ankle: roughly 70-78
degrees off vertical at default config, rotating the foot toes-down by the same amount.

- **Fix (small):** lock the ankle ORIENTATION the same way its POSITION is already locked. Capture the
  standing foot rotation in root space at bind time, then write
  `foot.rotation = root.rotation * footRotRoot` after the IK solve. Optionally Slerp by crouch amount
  to avoid a pop.
- **Must be done TWICE** (`RemotePlayerManager` and `LocalPlayerBody` are verbatim duplicates) or
  hoisted into one shared helper - which is exactly why the defect exists in two places.

### 5. Torso stuck pitched fully down on a peer's screen

CONFIRMED, root cause found (verified). **My leading hypothesis was REFUTED** - it is not a stale
transform reference. The sender deliberately avoids `Camera.main` and reads no camera transform at all.

`PlayerSyncManager.cs:272-302` picks the look pitch by **maximum absolute value** across
`FindObjectsOfType<MouseLook>()`, on a documented-but-false assumption that only one instance has a
non-zero `rotationY`. Vanilla has at least five (player yaw, player pitch, bed look, BoatCamera orbit
yaw, BoatCamera orbit pitch). `rotationY` is a private accumulator written only in `MouseLook.Update`,
so a component that gets `enabled = false` (e.g. `BoatCamera.SwitchOff`) **freezes its last value
forever** - nothing in vanilla or the mod ever resets it.

A parked orbit pitch sitting at its -60 clamp wins the max-abs contest and decodes to a 54.2 degree
spine fold against a 55 degree cap: visually maxed, exactly as reported. It looked fine in their own
first person because the mod only READS `rotationY`; their head look is driven separately. The camera
toggle "fixed" it by making that instance live-driven again.

- **Fix (small, A):** sample by IDENTITY, not magnitude. Cache `Refs.ovrCameraRig`'s `MouseLook` and
  read only that instance.
- **TRAP, do not do this:** filtering on `ml.enabled` inverts the bug. During orbit cam the player
  looks are DISABLED and the boat looks ENABLED, so an enabled-filter would make the avatar mirror the
  orbit camera instead of holding the player's last first-person pitch.
- Duplicated verbatim in `LocalPlayerBody.cs:317-347`, including the wrong comment. Extract one helper.

### 6. NPC ship visible to the host, invisible to the client

CONFIRMED, root cause found. (Verifier rejected the finding's log framing but supplied a STRONGER
proof; corrected version below.)

**One-shot guest cache with no self-heal.** `NPCBoatSyncManager.FindNPCBoat` (`:606-634`) rebuilds only
when `!_cacheInitialized`; `BuildCache` (`:639-653`) sets that flag unconditionally and populates from
`FindObjectsOfType<NPCBoatController>()`, **which excludes GameObjects deactivated by vanilla distance
culling**. The flag is cleared only in `Reset()`, called on lobby-leave and teardown - never during a
session.

So the host's 1Hz keepalive resend (`NPCKeepaliveInterval`), which exists precisely so a stationary
boat converges, is **completely defeated**: every keepalive hits the same dead cache. Guest log shows
131 receipts and 0 applies over 2m22s.

Proof (the corrected one): `BuildCache` logs through the UNGATED `NPCBoatApply`. Zero `[NPCBOAT:APPLY]`
lines in the capture windows proves `BuildCache` did not run in them, i.e. the flag was already latched
before the first receipt.

"Docked" is why it was provable: the ~1.05s packet spacing IS the 1Hz keepalive, which only fires for a
boat that moved under 0.1m and 1 degree per poll - a moored hull.

- **Fix (small, recommended first):** rate-limited rebuild on cache MISS (rebuild if
  `Time.unscaledTime - _lastCacheBuild > 2f`). Guest-only, no wire change, no invariant touched.
- **The distant-NPC half is a SEPARATE issue:** `MaxSyncDistance = 2000f` (`:151`) is far tighter than
  vanilla's 10000m visibility cutoff, so the client renders **uncorrected local ghosts between 2km and
  10km**. That is why the far-off vessel also looked wrong. Fix with distance-tiered rates, not a flat
  increase.
- **Logging hazard, fix alongside:** the path-mismatch warning at `:530-535` has no throttle and joins
  the ENTIRE cache key set into the log at up to 5Hz for a whole session.

### 7. Held items look laggy

CONFIRMED, root cause found (verified). Two compounding defects:

1. **No interpolation.** The held item is streamed as a raw transform on the 20Hz unreliable
   `PlayerPosition` packet, and the receiver hard-snaps it every frame
   (`ItemSyncManager.cs:986 item.transform.position = worldPos;`). Grep for Lerp/SmoothDamp in
   `ItemSyncManager` returns nothing. Vanilla holds an item ~1.15m in front of the camera, so a normal
   180 deg/s mouse-look moves it ~3.6 m/s = **~18cm of teleport per packet**.
2. **Phase mismatch.** The avatar body IS interpolated (`SmoothDamp`, smoothTime 1/15s = 66.7ms,
   `RemotePlayerManager.cs:696/721/731`) and ticks in LateUpdate, while the item snaps in Update. The
   body trails its own target by ~67ms while the item sits at the newest raw sample, so the item
   visually detaches from the hand and swims.

Packet loss compounds both: unreliable with no extrapolation means a dropped packet freezes the item
50-100ms then jumps.

- **Fix (cheap interim, ~1-2h, NO wire change):** SmoothDamp the item toward its target with the same
  1/15s smoothTime the avatar uses, in the same space the state is stored in (boat-local when
  `IsOnBoat`, world-real on land), and move `UpdateRemoteHeldItemVisuals()` from Update
  (`ItemSyncManager.cs:775`) into a LateUpdate call issued after the avatar tick.
- **Fix (correct architecture, ~1 day):** send the item pose in the holder's GoPointer/camera-local
  frame (a near-constant offset, so 20Hz is ample) and reconstruct each LateUpdate against the
  avatar's already-smoothed pose.
- **LANDMINE, would ship broken:** the host RE-SERIALIZES `PlayerPosition` field by field when
  relaying (`Plugin.cs:1204-1236`). Any new trailing block must be written there too or guests behind
  the host lose it. There is a documented precedent for exactly this bug with the crouch byte at
  `:1228-1231`.
- Do NOT bother with a rate bump alone: it halves the stair-step, fixes neither the phase mismatch nor
  packet loss, and multiplies relay traffic.

## 8-9. Missing sync for existing game features

### 8. Mooring rope hold has no visible animation

### 9. No remote animation for object interactions

Telescope, quadrant, lantern held in inventory, hammer, sail/rope winch operation, helm, and
essentially every other interaction.

ANSWERED: it is ONE mechanism plus N declarations, and it splits into two tiers with very different
costs.

Today the remote avatar has exactly THREE animation inputs: deck-relative walk speed, a crouch byte,
and a look-pitch byte. **Zero interactions feed it.** Every interaction system syncs the OBJECT's
state and lets each machine's vanilla code redraw the object, while the avatar stands there doing its
walk/idle cycle. This is deliberate: `RemotePlayerManager.StripForAvatar` destroys the Animator and
NPCAnimations on the cloned body ("static body for v1", `:1079-1084`). Vanilla ships no player
animation clips to reuse.

**TIER A - anything HELD (spyglass, quadrant, lantern, hammer, rod, bucket, oakum, broom, pipe).
NO WIRE CHANGE AT ALL.** The held item's pose is already streamed in every 20Hz `PlayerPosition`
packet. Pointing a 2-bone arm IK at that pose covers every held tool at once, with zero per-item
declarations. The 2-bone solver and rig refs already exist for the crouch leg IK
(`RemotePlayerManager.cs:459-499`), and Shoulder_L/R + Elbow_L/R are already located (`:293-294`).
This is by far the best value in the whole animation item and it should be done first.

**TIER B - fixed objects (helm wheel, winch/capstan, bilge pump, sail pusher, ladder).** Needs ONE new
actor-keyed packet, because the BOAT-CONTROL packets (RopeState/HelmState/HelmInput/HelmLock/
AnchorEvent/MooringState/Push*) and OBJECT-STATE packets (NavItemState, CookingState, TrapdoorState,
CleaningStroke, NailState, LightState) carry no SteamId, so a receiver cannot tell WHICH crewmate
turned the wheel. Suggested packet id 220. After that channel exists, each new interaction is a table
row (pose id + target transform + phase driver).

Note: **bed lie-down is NOT Tier B** - `SleepRequestPacket.AuthorId` already exists and is host-relayed
with the author preserved, so every machine already knows who got into a bed.

- **Prerequisite refactor (do first):** `RemotePlayerManager.RemoteAvatar` and `LocalPlayerBody` are
  near-verbatim duplicates of the same posing math (`RemotePlayerManager.cs:326-499` vs
  `LocalPlayerBody.cs:238-478`) with comments demanding they stay identical. Every new pose must
  otherwise be written twice.
- Item 8 (mooring rope) is a Tier A instance and comes almost free once the arm IK exists.

### 12. Quartermaster mode

**Prior art: none in tracked code, docs, git history or commit messages.** The only design intent
that exists is a sketch in the maintainer's notes: host appoints the QM (default host, reassignable,
reverts to host on leave), QM picks a divvy mode from Shared / Manual-allowance / Even-split /
Percentage, MVP leaning Shared + Manual + Even-split with Percentage as phase 2.

**Current model, established:** ONE shared wallet, host-authoritative. Vanilla `PlayerGold.currency`
is a static `int[4]` global with no per-player concept; the host is its sole writer and guest spends
are host-routed. That is exactly why this is tractable - guests already never authoritatively write
their wallet, so "shared" becomes "per-player bucket" mostly by making `CurrencySync` per-recipient
instead of a broadcast clone.

- **Approach A (recommended MVP spine, small):** keep `PlayerGold.currency` meaning "MY money" on each
  machine. Host holds `Dictionary<SteamId,int[4]>` buckets. Change
  `EconomySyncManager.SendCurrencySync` (`:100-115`) from a broadcast clone to a per-peer targeted
  send of that peer's bucket, and re-point the host charge sites at the requester's bucket.
- **Approach B (ship-first slice, small):** QM role + roster UI + appoint/relinquish + a permission
  gate on big-ticket spends, money still one shared pool. Reuses the existing "Only the captain can
  recover the boat" gate+toast pattern (`SurvivalPatches.cs:547-549`). Governance without accounting.
- **HAZARD to design around:** two existing paths infer transaction success from a DELTA on the host's
  `PlayerGold.currency` array (`EconomyPatches.cs:998-1009` shipyard confirm, and `:119-131` market
  feed state with readers at `:169`/`:209`). If per-player buckets stop that array representing the
  charged wallet for guest-routed trades, **both inferences silently mis-fire.**
- Not every money path is host-routed today (the onsen bath charge is one that is not), so an audit of
  spend AND income sites is a prerequisite for any bucket model.

### 14. Character model / player model selection UI

Players should be able to pick their appearance, so crewmates are visually distinguishable.

Placement options raised: a settings/options page, a wardrobe furniture prop, or a head icon in the
co-op escape menu (`UI/CoopPauseMenu.cs`, which already exists and is ours).

Not yet investigated. Open questions before it can be sized:

- What distinct player models or materials does vanilla actually ship? The remote avatar is a CLONE of
  the local player body (`RemotePlayerManager.StripForAvatar`), so today every crewmate is literally the

The escape-menu icon is likely the cheapest entry point since that menu is already ours to modify.
A wardrobe prop is the most in-fiction but needs an interaction and placement, and would overlap with
whatever comes out of item 10 (chair sitting) for interaction plumbing.

## Co-op save seeding (from the 2026-08-05 two-machine playtest)

- **Seed a fresh install's world by silently running New Game, instead of refusing.**
  `CoopSave.EnterCoopSaveContext` seeds the phantom by copying the guest's most recent solo save. On an
  install with no saves at all there is nothing to copy, and as of v0.3.0 that refuses with a panel
  telling the player to start a game once first. That is honest and cheap, but the better experience is
  to build the world for them and join. Deferred because it means driving the new-game flow, and
  breaking new-game to improve a narrow first-run case is a bad trade.

- **One co-op world instead of one per host.** The phantom is keyed `coop_session_<hostId>.save`, so
  sailing with a host you have not met re-seeds from your solo world and your co-op character appears to
  reset. A single co-op slot would give a player one consistent co-op character whoever they sail with.
  The per-host split exists to keep hosts' world state from bleeding between crews; worth deciding
  deliberately rather than leaving as-is by default. Touches save handling, so it wants a review pass.

- **Blinders over the join. SHIPPED in v0.3.0** as `UI/JoinProgressScreen`. Kept below for the reasoning,
  and for what the build actually did differently from this plan:
  - The screen goes up when the player COMMITS to a join, not when control is taken away. Covering only
    the control-disabled window (STEP 2 onward) was tried first and left 68% of a measured join on
    screen, because the wait for the host's snapshot and the title path's 1.5s settle both precede it.
    That meant also freezing the player at the start, since nothing else does until STEP 2.
  - It CUTS to black rather than fading. Step.Placing lands in the same frame as the throw onto the
    perch, so any fade reveals exactly what the screen exists to hide.
  - Vanilla's sleep fade (`Blackout.FadeTo`) was NOT borrowed: it lerps on scaled `Time.deltaTime`, and
    joining a paused/docked/sleeping host at timeScale 0 is normal, where that fade never completes.
  - Checkpoints RETARGET the bar rather than snapping it. Three of the six steps measured at 0.0s, so
    snapping made the bar teleport between floors instead of moving.
  - `GameState.loadingScenes` is only a usable fraction when more than one scene is streaming; the common
    join streams exactly one, making the fraction a flat zero for the whole longest step.

  Original plan follows.

  A joining guest currently watches their own world load and sit there before
  being pulled onto the host's boat, which reads as jank even when it is working correctly. Black the
  screen for the duration with a progress indicator, ideally borrowing vanilla's sleep fade so it looks
  native rather than like a mod overlay. The window already exists and is well defined: the join
  disables player control and shows a "Joining the crew..." banner from STEP 2 to STEP 6 in
  BoatStateApplicator, so the overlay has an unambiguous start and end.
  ORDER MATTERS: do this only once joins are confirmed reliable. A blackout over the v0.3.0
  timeScale-0 bug would have shown 45 seconds of loading bar followed by the game quitting, with nothing
  to diagnose from. A loading screen makes a working join feel finished and a broken one invisible.
  PROGRESS: track it on real events, not a timer. The join is already a sequence of named steps
  (STEP 1-7 in BoatStateApplicator), so the bar can advance as each completes and carry a live label -
  "Loading terrain", "Placing you aboard". Most steps are discrete and instant, so "3 of 7" is true.
  The terrain wait is the long one and Unity's scene loads expose AsyncOperation.progress, so that
  segment can fill genuinely. The snapshot transfer varies with world size and should read as an
  indeterminate "waiting for the captain's world" rather than a fake percentage. A smooth 0-100% would
  be invented. The label also doubles as diagnostics: a hung join then says WHERE it hung, which is
  exactly what was missing when the timeScale-0 bug was being chased.
  REFINEMENT (the above was too purist - every loading bar interpolates, and that is fine): the
  CHECKPOINTS must be real, the motion between them need not be. Weight each step by its typical cost
  (terrain gets the big slice, the instant ones get slivers), SNAP to a checkpoint when that step
  genuinely completes, and ease toward the next one while asymptoting just short of it rather than
  arriving. A fast step then catches up quickly, a stalled step creeps and slows instead of freezing,
  and the bar never goes backwards or claims to finish early. Terrain can use real
  AsyncOperation.progress within its own slice instead of easing.

## Eating and drinking animations are not replicated (v0.2.40)

Raised in the same playtest: a crewmate drinking or eating plays no animation on anyone else's screen.
Not deferred from anywhere, just never built. Needs are deliberately INDEPENDENT per player
(SurvivalSyncManager's send/receive paths all early-return by design), so consumption never crosses the
wire at all and there is nothing for a remote machine to react to.

Wants a small cosmetic-only signal - who consumed, and which class of item - rather than any needs
sync, so it cannot become a route for one player's survival state to reach another's.

SCOPE, refined by the 2026-08-05 playtest: water barrels and food already read correctly from the other

free. The MUG does not, so it is the one that actually needs a signal. Check which other consumables
animate through held-item motion alone before building anything - the list may be short enough that this
is one item, not a system.

## HMS Leopard cannons are not synced at all (found 2026-08-06)

**`grep -ri cannon src/` returns NOTHING.** We sync the Leopard's gunports (the hatch doors), the
cutter and the bell, and have never touched the cannons. Firing one is invisible to the rest of the
crew: they hear nothing and see no flash or smoke.

Not a regression and not a version problem - `Controllers/CannonController.cs` has existed since
Leopard **v1.4.0** (2026-07-01), so it was already there in v1.5.1, the version this mod integrated
against. It was simply never covered.

**This is cosmetic-only, which makes it cheap and safe.** `CannonController.Fire()` plays audio, a
muzzle flash, smoke and barrel particles, then runs `Recoil()`. There is no projectile, no damage and
no gameplay state, so there is no authority question - it can be a fire-and-forget broadcast exactly
like the existing `BellRing` (packet 219), and a dropped packet costs one missed puff of smoke.

Shape:

- Patch `CannonController.Fire()` and broadcast (boat name, cannon identity, single-or-broadside).
- Cannons are addressable by the same scheme `FireAll()` already uses to find them:
  `boat leopard/structure_container/CANNONS/{upper|lower}/{port|starboard} {1..6}`. Use that path as
  the identity rather than an index, so it survives Leopard reordering them.
- `FireAll()` is the Shift-click broadside AND a Shift+K hotkey in `CannonController.Update()`, so
  there are TWO local entry points. Broadcast the broadside as ONE message and let receivers replay
  the sequence, rather than sending twelve.
- The receiver must call `Fire()` through an apply-guard, or the patch re-broadcasts what it just
  replayed. Same shape as every other replayed visual in this repo.
- `Fire()` early-returns unless `ready` and not `firing`, and those are per-cannon local state. A
  receiver whose copy is mid-recoil will silently drop the replay, which is acceptable.

Gate it behind the existing Leopard compat, and remember the whole crew is already required to have
Leopard at a matching version, so there is no "peer lacks the mod" case to design for.

WHAT ACTUALLY BREAKS, and what does not. The VERSION is read dynamically from BepInEx metadata and
goes into the handshake token, so a crew all on a newer version still matches itself and joins - a mod
update does NOT break joining. What breaks is the REFLECTION into each mod's internals (for SE:
`SaveSailConfig` / `LoadSailConfig` and the rig-blob shape). If a name or shape moves, the relevant
`_reflectionOk` goes false and that mod's sync disables itself for the session with a log warning.
So the failure mode is a silently missing feature plus a log line, not a crash - which is safe, and
also easy to not notice for several releases.

PER RELEASE, the check is cheap:
1. Look up each mod's current version on Thunderstore/Nexus and compare against the table above.
2. For any that moved, decompile the new build and diff the members we reflect on.
3. Update the table, and the `(decompiled X.Y.Z)` note in that mod's Compat file.
4. If a member moved, decide: follow it, or leave the graceful-disable and say so in KNOWN-ISSUES.

## Cold-launch invite auto-join (deferred from v0.3.0)

Accepting a Steam invite while the game is NOT running launches Sailwind but does not carry the player
into the session. Confirmed 2026-08-06; deliberately deferred, because it wants a focused release
rather than a corner of a large one.

Current behavior after the v0.3.0 invite fix, which is an acceptable resting point: the invite IS
recorded on launch, so it appears in the title-menu friends list and the player joins with one click.
What is missing is only the automatic part.

The hard part is ORDER. Steam delivers the lobby to a cold-launched game through the launch command
line (+connect_lobby) or an OnGameLobbyJoinRequested that fires during startup - well before the
plugin, Steam callbacks, or the StartMenu exist. Anything that races that will look exactly like the
bug it is meant to fix.

Wants: capture the lobby id from the command line at Awake, hold it, and hand it to TitleJoinManager
once the StartMenu is up and Steam is initialized - i.e. the same funnel the title friends list uses,
entered from a different door. Also needs a decision about what happens when the phantom load fails at
that point, since the player never chose to be there and a failed cold join should return them to a
usable menu rather than a black screen (see the animsPlaying trap the v0.3.0 timeout fix handles).
