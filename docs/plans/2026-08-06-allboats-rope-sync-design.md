# All-boats rope/sail sync: design + adversarial review (2026-08-06)

Produced by a 12-agent workflow (5 analysis lenses, 3 competing designs, 1 judge, 3 adversarial
verifiers). ALL THREE verifiers refuted the synthesized plan. Read the DEFECTS section before
implementing any step: several steps as written would ship a regression worse than the bug.

## Winner: Per-boat BoatControlState, mirroring BoatSyncManager, plus a host round-robin rope reconcile

It is the only design that fixes both halves of the problem, and it does so with a refactor this repo has already shipped once. The bug has two independent causes: (a) ongoing sync reaches only GetCurrentBoat(), and (b) nothing ever re-asserts a rope nobody is operating, so a missed edge is permanent. C fixes only (b); B fixes (b) plus a sliver of (a). A fixes both, and the ordering matters: adding a host re-assert while the local-author set stays narrow converts a currently-harmless gap into a new regression. Today, hauling a winch from a dock (GetCurrentBoat() null, ControlSyncManager.cs:181-182 returns) or on a rafted neighbor boat sends nothing and stays local. Under C's reconcile that haul is REVERTED within RopeReconcileQuietPeriod + interval, because no local send ever stamps _ropeActivity for that boat. B narrows but does not close the same hole (its local-author set is current boat + anchor boat, so an adjacent-boat winch is still asserted over, and its receiver-side operating exception only fires where a state entry happens to exist). A's per-boat poll makes IsLocalOperatingRope answerable for every active boat, so the haul authors, stamps activity, blocks the reconcile, and converges the host - no revert. Second, A's diff is the largest but its novelty is the smallest. BoatSyncManager.cs:30-75 plus :415 is literally this refactor already performed on the sibling manager ("the pre-v0.2.28 single-boat ApplyBoatTransform body operating on a BoatSyncState entry instead of instance fields"), and the healing primitive ResendRopeForBoat (ControlSyncManager.cs:654-668) already exists, is already host-only, and is already called from two sites. B is the only design that adds a wire packet, a seq/dedupe layer, a second deferral queue, and two unordered write paths for the same rope - its own risk list admits the ordering gap. Third, A is the only design that fixes the two live defects that fall out of the mapping regardless of the multi-boat bug: the settle terminal is unreachable when GetCurrentBoat() is null (the sweep at :277-287 sits below the return at :182), and a boat change wipes armed terminals via _ropeFinalSent[j] = true at :207. Hoisting the sweep next to SweepMooringTerminals fixes both for free. A also converts the four "stamp only if this is GetCurrentBoat()" guards (:588, :1079, :1118, :1194) from workarounds into exact per-boat stamps, and repairs the latent cross-boat anchor false positive at :394-406 that would otherwise make any boat-looping refactor broadcast six boats' anchor ropes at 10Hz.

## Open questions flagged by the judge

- Should a remote reliable IsFinal be allowed to land on a rope the local player is mid-haul on? Today TryApplyRopePacket (:521-609) has no operating check and the documented policy at :447-451 is last-writer-wins. Once a periodic reconcile exists, a 20s assert can yank a rope out of a peer's hands if the 2s quiet window misses. The narrow graft is: skip the apply only when state.RopeFinalSent[i] == false (a local terminal is armed for that exact rope), which leaves ordinary two-players-on-one-winch contention unchanged. Decide before Stage 2 ships, because it changes an existing documented behavior.
- What is the acceptable reliable-packet budget for the reconcile? 20s per boat is ~102 uncoalesced reliable RopeState per 20s per peer (~5/sec, ~300 B/s). RopeState is deliberately off the coalesce whitelist (P2PNetworkManager.cs:303-325) so each is its own ProcessPacket against the per-frame budget. Raise the interval first if a playtest shows intake pressure; the batched BoatRopeVector (packet 223, confirmed free) is the escalation, not the opening move.
- Per-boat anchors are a deliberate behavior change, not a side effect. Carrying boat B's anchor while standing on boat A, or on a dock, will now broadcast boat B's anchor rope - impossible today because the poll returns at :181-182 when GetCurrentBoat() is null. This is correct (the player really is paying out that rope) but it intersects playtest section 9 (overnight anchor). Watch it in the next session, or gate it behind a flag for one release.
- The reconcile makes the host's live rope length authoritative for any boat nobody is operating, so an unknown host-local contaminant outside the two excluded windows (shipyard active, SE trim restore pending) now propagates to the crew on a 20s cadence. The signature would be slowly reverting sails every 20s, which is distinctive. Is there a third contaminant window worth excluding - a boat mid stream-out, or one whose rope cache just went dead per the Andriy failure at BoatUtility.cs:180-185?
- Should guests poll all active boats at the secondary rate, or only their current boat plus boats where they are actually operating something? The plan has every peer polling every active boat, which is what makes dockside and adjacent-boat authoring work, but a guest can never author a boat it is not touching, so most of that scan is pure cost. Confirm on the profiler (:102/:128) before deciding whether the divider needs raising on guests specifically.
- Correctness of the whole poll set depends on BoatUtility.ClearCaches call sites staying complete (Plugin.cs:870, :1018, :1304, LeopardSyncManager.cs:231). A boat spawned at runtime without a ClearCaches call is invisible to both the poll and the reconcile for the rest of the session. That is an inherited invariant (Plugin.cs:1015-1017 records the historical failure) but the blast radius grows once rope sync depends on it - worth an audit pass in the same PR.

## DEFECTS found by adversarial review (3/3 lenses refuted)

### Defect 1: Step 21 (Stage 2) - ReconcileRopesRoundRobin's exclusion set: IsBoatShipyardActive + IsTrimRestorePending

**Defect:** The reconcile calls ResendRopeForBoat, which is the ONE rope send path with no IsLocalOperatingRope gate (ControlSyncManager.cs:654-668 broadcasts every rope's live currentLength as a reliable IsFinal). Its two exclusion windows do not cover the host's single guaranteed rope-trim contaminant: applying another peer's shipyard customization. ShipyardSyncManager.ApplyCustomization (:1245-1278) calls vanilla customization.LoadData(saveData) and then ONLY BoatUtility.InvalidateRopeCache - there is no SnapshotRopeTrim/RestoreRopeTrim on that path at all. The file states the consequence itself at :918-921 ('every recreated RopeController comes back at its PREFAB DEFAULT length') and at :464-467 ('(host only) re-seed every current rope length so crew whose sails were rebuilt to defaults by LoadData converge'). That repair (ReseedRopesAfterShipyardExit -> ResendRopeForBoat, :501) is host-only inside (ControlSyncManager.cs:656 `if (!Plugin.IsHost) return;`) and is triggered only by the EDITOR's own DischargeShip - so when the editor is a GUEST it is a no-op and the HOST is never repaired. The SE trim machinery does not cover it either: preserveTrim requires Compat.SECompat.IsInstalled (:944-946), so a no-SE crew gets no restore at all, and even with SE the 215 arrives AFTER the 43, so SnapshotRopeTrim (:1008) captures the already-defaulted lengths. _trimRestorePending (:118) is added at :974 and removed in the coroutine finally at :1054, i.e. exactly one frame, and is never added when preserveTrim is false. So both of the plan's guards read false at the moment the contamination is permanent.

**Failure scenario:** Vanilla crew (no Shipyard Expansion), host H plus guest G. G takes the brig `BOAT medi medium (50)` (38 ropes) into a shipyard and adds a mast. G's ShipyardSyncManager.PollForChanges sends packet 43; H's OnCustomizationReceived -> ApplyCustomization -> LoadData rebuilds all 38 RopeControllers at prefab default. H's poll suppresses the delta (IsLocalOperatingRope false), so nothing leaks - today this stays a silent one-sided desync. G exits: _shipyardActiveBoats.Remove fires on both machines (:1298/:1342), and G's ReseedRopesAfterShipyardExit calls ResendRopeForBoat, which returns immediately on a guest. Now IsBoatShipyardActive(brig)==false and IsTrimRestorePending(brig)==false. Within RopeReconcileInterval (20s) the round-robin cursor reaches the brig, every guard passes, and ResendRopeForBoat broadcasts 38 reliable IsFinal RopeStates carrying prefab defaults. Every peer's TryApplyRopePacket applies them and stamps LastRopeLengths, so no peer's change detector trips and nobody re-authors. G's correct trim - the trim G just built - is destroyed by the host's echo of G's own edit, and the next cycle re-asserts the same defaults 20s later, so the crew cannot repair it except by physically re-hauling all 38 ropes (which they must do again after every guest shipyard visit). Symptom is exactly the 'slowly reverting sails every 20 seconds' signature the plan lists as the thing to watch for.

**Fix:** Do not treat the host's live rope array as trustworthy for a boat whose sails this machine rebuilt from a peer's packet. Either (a) give ApplyCustomization the same snapshot/restore ApplyRigBlobNow has - SnapshotRopeTrim before LoadData, RestoreRopeTrim one frame after, un-gated on SECompat.IsInstalled (this also fixes the pre-existing silent desync); or (b) add a third exclusion: a per-boat `_ropeTrustSuspended[boatName] = Time.time` stamped in ApplyCustomization, ApplyRigBlobNow, and in RestoreRopeTrim's two stand-down returns (ShipyardSyncManager.cs:1064 join-in-progress, :1068 boat destroyed), cleared only when some peer re-authors a rope on that boat (OnRemoteRopeChanged/OnLocalRopeChanged), and checked by BOTH ReconcileRopesRoundRobin and ResendRopeForAllBoats. Do not ship Stage 2 with only the two named windows.

### Defect 2: Steps 3 and 4 (Stage 0) - ResendRopeForAllBoats + the RunJoinStep("ResendRope") swap at Plugin.cs:3147

**Defect:** Same ungated-broadcast root cause, but it ships in Stage 0, which the plan calls 'independently shippable ahead of the refactor', so it lands even if Stage 2 never merges. Step 3's skip list (null, !activeInHierarchy, IsBoatShipyardActive, IsTrimRestorePending) contains no test for whether this machine's copy of a boat's rope lengths has ever been validated. Today the join re-seed covers exactly one boat - the one the host is standing on, hence the one boat the host's own poll has been authoring and whose trim the host owns. Extending it to FindAllBoats() extends it precisely to the six boats whose host-local rope state has never been produced or checked by anything, and step 4 notes OnLocalRopeChanged uses SendToAllReliable (:431-432), so it is a full-crew broadcast, not a targeted seed to the joiner.

**Failure scenario:** Host H, guests G1 and G2. Earlier in the session G1 edited the sanbuq `BOAT dhow medium (20)` in a shipyard; H applied the 43, rebuilt its sails to prefab default, and was never repaired (see the previous defect). Hours later G2 disconnects and rejoins. RunJoinStep("ResendRope") now calls ResendRopeForAllBoats: the sanbuq passes every filter (not null, active, no shipyard open, no SE restore pending) and H broadcasts its 7 prefab-default rope lengths reliably to G1 and G2. G1's correct sanbuq trim - nobody is aboard, nobody is operating a winch, so no peer re-authors - is overwritten permanently. The same broadcast fires on every subsequent join. Today this cannot happen: ResendRopeForCurrentBoat only touches GetCurrentBoat(), and H is on the brig.

**Fix:** Gate ResendRopeForAllBoats on the same trust predicate as the reconcile (see previous fix), and additionally consider making the join re-seed a TARGETED send to the joiner rather than SendToAllReliable - the 'heals the whole existing crew on every join' property the plan sells as a bonus is precisely what turns one machine's stale copy into a crew-wide overwrite. If the broadcast is kept, it must not be shippable ahead of the trust window.

### Defect 3: Step 9 - 'fill _pollNamesScratch/_pollBoatsScratch in one pass over BoatUtility.FindAllBoats() ... Resolve currentBoatName once from GetCurrentBoat()'

**Defect:** The plan's open question calls 'a boat invisible to FindAllBoats' an inherited invariant. It is not inherited for the poll. Today PollBoatControls resolves its subject from GetCurrentBoat() (ControlSyncManager.cs:181), which reads GameState.currentBoat.parent (BoatUtility.cs:68-77) and never consults the boat-name cache. Step 9 makes FindAllBoats() the sole source of the poll set and demotes GetCurrentBoat() to a name comparison. ## Invariants that must survive

- The stamp at ControlSyncManager.cs:241 runs on EVERY detected change, before and regardless of the operated gate. This is what makes a stale or foreign baseline cost one wasted tick instead of a stale accumulated delta on the next grab. Do not move it inside the gate.
- The rope settle terminal is armed ONLY by the operated-send branch (:266-268). Nothing else may write _ropeLastChangeTime / _ropeFinalSent / _ropeLastSentLength false-or-forward. That single discipline is why the gate-free reliable sweep at :277-287 can never broadcast unoperated state.
- The terminal ships _ropeLastSentLength[i] (the value captured at the last operated send), never the live currentLength at sweep time. Reason at :146-148: unoperated drift between the send and the sweep would be exported to the whole crew inside a reliable IsFinal.
- A remote rope apply must stamp the same slot the poll will read, or the poll re-broadcasts the value it just received. Currently TryApplyRopePacket:587-591, gated to the current boat.
- IsFinal governs the transport on both the send (:429-438) and the host relay (:455 `reliable: packet.IsFinal`). Terminals are reliable; deltas are unreliable. Any new reconcile path must keep that pairing or a dropped 'final' silently strands a rope again.
- A boat/rope-count change wipes the per-rope arrays; an array-IDENTITY-only change preserves them (:196-227). The asymmetry exists to avoid cancelling a pending terminal across a mid-operation sail rebuild.
- Wire rope indices are positional into BoatUtility.GetRopeControllers, which is stable-sorted by GetStableRopeKey so host and guest agree (BoatUtility.cs:147-166, :215-275). Local caches may be re-keyed however is convenient, but the packet's RopeIndex meaning must not change.
- The operated-rope gate applies on host and guest alike (:246). Unoperated local rope movement is never authoritative on any machine. If a host-authoritative reconcile is added it must be an explicit separate path (like ResendRopeForBoat), not a relaxation of this gate.
- Reset() (:1854-1882) is the session-teardown ledger. Every new per-boat structure must be added there; note _lastHelmLocked is already missing from it.
- Exactly ONE reliable IsFinal RopeState per settle per (boat, rope): never zero (the v0.2.24 'sail stuck at intermediate position' stranding) and never a stream. The latch is set BEFORE the send (ControlSyncManager.cs:283) and is cleared only by a fresh operated delta (267).
- The terminal ships the length captured at the last OPERATED send (_ropeLastSentLength, line 268 -> 285), never the live currentLength at sweep time. Re-reading currentLength would export unoperated drift reliably to the entire crew (field doc 146-149).
- Only ropes the local player is physically operating ever broadcast: winch grabbed by the local pointer, or the anchor rope while the local player carries the anchor item (246, 385-408). This is what keeps a multi-boat poll from echoing the world back at itself.
- _lastRopeLengths is stamped on EVERY detected change, including suppressed ones (241), so a later grab diffs only movement made while grabbed rather than an accumulated stale delta.
- A remotely applied rope must never be re-broadcast by the poll (echo guard, 582-591). Per-boat arrays make this exact instead of conditional on GetCurrentBoat.
- Per-rope send state survives an identity-only rope-array rebuild (same boat, same count, fresh array) so a mid-operation shipyard/SE sail rebuild cannot cancel a pending terminal (212-227).
- Wire rope indices are the stable-sorted BoatUtility.GetRopeControllers order and nothing else (BoatUtility.cs:147-166, 215-275); host and guest agree only because both resolve through that call.
- RetryPendingRopes runs before PollBoatControls every tick, so a deferred join seed is applied and absorbed into the change-detection baseline in the same tick the controllers appear (110-114).
- The 10Hz gate stays multiplied by SleepSyncManager.HostSleepSendIntervalScale (107) so a per-boat poll cannot re-create the sleep-warp packet flood; note RopeTerminalDebounce compares raw Time.time and is therefore already warp-compressed, which is harmless for a one-shot latch but must not be turned into a repeating send.
- The receive path stays boat-agnostic and the wire format stays unchanged: TryApplyRopePacket resolves by boat name (524) with a rope-name fallback (543-555), and the host relays with reliable: packet.IsFinal before applying (452-456).
- Rope index i must keep meaning the same logical rope on every machine. Every send and apply path resolves through BoatUtility.GetRopeControllers, whose stable sort (BoatUtility.cs:160, key at :215-275) is what makes the wire index and the positional join-snapshot array agree. Per-boat arrays must be sized and indexed from that same array for that same boat, never shared or maxed across boats.
- The echo guard must remain exact: a length written by a remote apply must be stamped into the change-detection cache for THAT boat, so the poll never re-broadcasts it. Today TryApplyRopePacket (ControlSyncManager.cs:587-591) skips the stamp entirely when the packet is for a non-current boat, which is only safe because the poll ignores non-current boats. If the poll starts covering all boats and the stamp stays skipped, every remote rope change becomes a local echo candidate.
- The operated-rope gate stays the sole authority on what is broadcast: winch grabbed via the local pointer, or the anchor rope while the local player carries the anchor (ControlSyncManager.cs:385-408). Its field-report justification at :156-164 (sails "unfold as if holding W" on the other machine) must survive the refactor untouched.
- A pending reliable settle terminal must survive an array rebuild. ControlSyncManager.cs:217-224 spells out why the identity-only rebuild preserves the four parallel arrays: wiping them "would cancel a pending IsFinal rope terminal ... and recreate the v0.2.24 'sail stuck at intermediate position' class."
- The terminal must ship the length captured at the last operated send, not the live length at sweep time (ControlSyncManager.cs:147-149 and :284-285). Per-boat arrays must keep _ropeLastSentLength paired with _ropeFinalSent for the same index.
- The rope-array identity check must stay. ControlSyncManager.cs:168-176 documents that a same-count same-name sail rebuild leaves the winch map keyed on destroyed RopeControllers, so IsLocalOperatingRope misses on every rope and all local broadcasts go silently dead until rejoin. Under per-boat state this check has to run per boat, not once for the current boat.
- Reset() must clear the new dict. ControlSyncManager.cs:1854-1882 already clears every other per-session map, and BoatSyncManager.cs:963 does `_boatStates.Clear()` for the same reason.
- Nothing in the poll may throw. The two comparable all-boats loops both isolate per boat: BoatStateCollector.cs:35-49 wraps each boat in try/catch after "ONE boat that threw while being read took down the ENTIRE join snapshot", and BoatStateApplicator.cs:379-392 does the same on apply. A 10Hz loop over 7 boats needs at least a null check per entry and probably the same per-boat try.
- Rope indices on the wire always come from BoatUtility.GetRopeControllers' stable sort order (BoatUtility.cs:147-166), which is the same array the join snapshot's RopeLengths is matched against positionally. Any new per-boat cache indexes into that array and nothing else.
- The host relays every RopeState with SendToAllExcept(sender) BEFORE attempting a local apply, and does so whether or not it can resolve the boat or rope locally (ControlSyncManager.cs:452-456).
- Only ropes the local player is actually operating are ever broadcast (ControlSyncManager.cs:246). Unoperated local movement (stick drift, load-time reef forcing, join-race defaults, the SE trim restore) must never reach the wire.
- The change-detection cache is stamped for every detected change, including changes that are not sent (ControlSyncManager.cs:239-241), so a later grab diffs only movement made while grabbed.
- The reliable settle terminal ships _ropeLastSentLength, the length captured at the last OPERATED send, never the live currentLength at sweep time (ControlSyncManager.cs:284-286).
- RetryPendingRopes runs before PollBoatControls in the same tick (ControlSyncManager.cs:114-116), and pending seeds are latest-wins per (boat, ropeIndex) with a realtime TTL.
- Deferred rope retry is guest-only (ControlSyncManager.cs:470).
- A remote apply's echo stamp uses the RESOLVED index (appliedIndex), which the name fallback at ControlSyncManager.cs:543-555 can move away from packet.RopeIndex.
- An identity-only rope-array rebuild preserves the per-rope send state; only a count change or a boat change wipes it (ControlSyncManager.cs:196-227).
- Reset() (ControlSyncManager.cs:1854-1882) clears every piece of rope state so nothing bleeds across sessions; any new per-boat map goes in there too.
- ShipyardSyncManager.MarkRopeAuthoritative is already keyed by boat name (ControlSyncManager.cs:579-580) and must keep being called on every applied rope packet, for every boat.
- A remotely-applied rope length must stamp the echo cache for the boat it applied to and must never stamp any other boat's. The cross-boat guard at ControlSyncManager.cs:587-591 becomes a per-boat lookup; drop it and the host's poll re-detects every guest value as a local change and re-broadcasts it, including a reliable terminal carrying a stale length that nothing will ever correct.
- _ropeFinalSent, _ropeLastChangeTime and _ropeLastSentLength must stay index-aligned with the SAME boat's GetRopeControllers array, and the identity-only rebuild path at :212-227 must keep PRESERVING them across a rope-cache invalidation. Wiping them cancels a pending reliable terminal, which is the v0.2.24 'sail stuck at an intermediate position' class.
- A rope index means 'position in BoatUtility.GetRopeControllers(boat)', a stable cross-machine sort (BoatUtility.cs:147-166, 215-275). Every piece of per-rope state must be keyed by (boat, index), never by index alone.
- The winch map must be rebuilt whenever a boat's rope array is re-derived, on both triggers: rope COUNT change and array IDENTITY change (:196-227). A stale map makes IsLocalOperatingRope miss on every rope and silently suppresses all local broadcasts, the v0.3.0 'host went dead after using the shipyard' failure (BoatUtility.cs:168-195).
- Unoperated local rope movement must never be broadcast by a guest (:243-253). That gate is the only thing standing between the crew and three machines imposing their local drift on each other, and it must survive any widening of the poll.
- RetryPendingRopes must still run before the poll for whichever boat it is seeding (:110-116), or the discovery tick stamps default lengths over an in-flight seed.
- A settle terminal ships the length captured at the last OPERATED send, not the live value (:284-286), so drift between the last haul and the sweep is never exported.
- Reset() must clear every piece of per-boat state (:1854-1882). A per-boat dictionary additionally needs eviction when a boat is destroyed or streamed out, or entries leak the way _recentNetworkMooringChanges and the winch map were explicitly fixed not to (:1862-1866, :1876-1877).
- Boats admitted to a shipyard on ANY peer (ShipyardSyncManager.IsBoatShipyardActive) and boats with an SE trim restore in flight (_trimRestorePending / MarkRopeAuthoritative) must be excluded from any assertion or broadcast path.
- The host relay must stay: a guest's rope change is a request the host applies and forwards to the other guests (:452-456). Nothing in a per-boat refactor should let a guest's value reach other guests without passing through the host.

## Traps

- Deleting the `BoatUtility.GetCurrentBoat()?.gameObject.name == packet.BoatName` clause at :588 to 'let the stamp work for all boats' while _lastRopeLengths is still one array. Concretely: host on the brig (38 ropes), a guest hauls the sanbuq's rope 5; the sanbuq stream writes 0.80, 0.81, 0.82... into slot 5 at 10Hz, which is the BRIG's rope 5 baseline. Most ticks this costs one suppressed-and-restamped iteration. But when the host is winching brig rope 5 and its length passes within 0.001 of a freshly-written foreign value in the same tick, the detector reads 'unchanged' - so no delta is sent AND :266-268 never arm, so no terminal fires when the host lets go. That rope stays at the pre-haul length on every peer for the rest of the session, silently.
- Cross-writing the terminal trio needs no coincidence at all. Any refactor that has a remote apply mark a rope 'settled' (`_ropeFinalSent[i] = true`) cancels a genuinely pending terminal on the current boat's rope i outright - the v0.2.24 'sail stuck at intermediate position' class, which the code at :218-223 already warns about in the other direction. The mirror image (a foreign arm) ships another boat's captured length as a RELIABLE IsFinal, which nothing ever re-sends.
- Calling IsLocalOperatingRope with another boat's rope. The winch branch fails safe (map miss -> false) but the ANCHOR branch (:394-406) tests _ropeCacheAnchor, the CURRENT boat's anchor, with no boat check - so carrying the brig's anchor reports 'operating' for the anchor rope of all seven boats. Gate a poll-all-boats loop with the unmodified method and you broadcast six boats' anchor rope lengths at 10Hz.
- Reasoning 'nobody is standing on that boat, so nobody can be operating its ropes, therefore skip the gate for non-current boats'. That inverts the fix: combined with the -1f sentinel at :206, the first tick after a join or a cache invalidation flags every rope of every boat as changed and broadcasts this machine's possibly-stale lengths for the whole world. It is the reported 'whoever boards a drifted boat first wins' failure, promoted to 'whoever loads first wins, without touching anything'.
- Assuming poll-all-boats fixes the reported bug. The changes that drift an unoccupied boat (SE rig rebuild to prefab defaults, load-time reef forcing, join-race defaults) are exactly what the operated gate at :246 suppresses - see the field-report comment at :157-164 and ShipyardSyncManager.cs:918-924. Wider polling adds detection for changes that are then all suppressed. Healing a drifted unoccupied boat needs a host-authoritative re-seed (ResendRopeForBoat, :654-668), which is a different code path.
- Making _ropeWinchMap per-boat-cleared while looping all boats.
